# Taste: UI/UX (Continuously Learned)

- Prefers modals/popups on mobile to slide up from the bottom as bottom sheets (with rounded top corners and a drag-handle indicator), matching native dropdown/sheet patterns, rather than appearing centered. Confidence: 0.9
- Wants form controls to be self-explanatory by default — e.g., date pickers should show a visible placeholder/label when empty instead of appearing blank. Confidence: 0.8
- When a real photo of the subject is available, prefers showing that photo with measurements/labels overlaid directly on it over showing an abstract graph — visuals tied to the actual object beat charts. Confidence: 0.6
- Values interactive image annotation (drawing lines, placing labels on a photo) as a first-class feature rather than static/read-only display — explicitly asked for the photo editor to support manual annotation tools (custom lines, arrows, and text labels) in addition to the auto-populated frame. Confidence: 0.8
- When a user lacks permission to view a screen, prefers silently redirecting them back into the main app (e.g., to index) rather than showing a dead-end "blocked" page. Confidence: 0.5
- Cares about pixel-level visual consistency — notices and reports small asymmetries (e.g., one side of a modal's border-radius being rounded while the other isn't) as bugs worth fixing, not nitpicks. Confidence: 0.5
- For annotating photos with measurements, prefers a document-scanner-style interaction over freehand drawing: auto-place a pre-made frame showing the real measurements, then drag its corner handles to warp it onto the actual opening in the photo. Confidence: 0.7
- Wants measurement annotations to be automatic, not manual: dimension lines and labels should auto-populate from the measured values, with label text running parallel to its line and the offset from the frame grouped/uniform. Confidence: 0.6
- Wants dimension/label text overlaid on annotated photos to be large and clearly readable — asked twice for bigger labels ("labels are microscopic" after the first bump) and will keep calling out small text until it's genuinely legible on the photo, not just relatively larger. Confidence: 0.8
- Wants a magnifier/zoom-loupe that follows the cursor while dragging a corner handle, showing a magnified view of the area under the pointer for precise frame alignment — the familiar image-editor magnifier pattern. The loupe must show the *actual* pixels under the cursor (correct region/scale sampling) — an offset or mismatched loupe was called out as broken ("the loupe isnt using the actual view of the point"). Confidence: 0.8
- Cares about animations/micro-interactions in the UI and treats losing them in a rewrite as a regression — asked "animations. did we throw them away" after the photo editor was rebuilt, expecting the agent to check git history and restore what was lost rather than accept the simplified version as final. Confidence: 0.5
- On mobile, the camera button must trigger the actual camera capture intent and the gallery button must open a photos-only picker — separate file inputs with their own attributes (capture for camera, plain accept="image/*" for gallery), never both buttons reusing one generic file picker. Confidence: 0.8
- Inside the magnifier loupe, only the crosshair lines should render — the corner-handle circles (and any other occluders) must not show up in the magnified view, since they'd obscure the precise alignment point. Confidence: 0.6
- Prefers the measurement dimension lines to sit exactly at the frame border points — "the borders should be the exact points where the measurement lines GO" — rather than offset outward from the frame as separate dimension lines. Confidence: 0.5
- Custom annotation lines/arrows must persist even when left unlabeled (label is optional); only text annotations with no content get dropped. Confidence: 0.6
- On mobile, form input boxes/holders must never overflow their container vertically — when a row of text fields is squeezed into cramped side-by-side columns (causing placeholder text to wrap and the holder to grow past the panel), the fields should stack full-width on narrow screens instead. The main app's mobile display was called out as broken ("display management is ass") over exactly this. Confidence: 0.7
- Dislikes large empty voids in label/value detail rows — `justify-content: space-between` in a wide column shoving short values to the far right edge was reported as "crazy amount of right padding or somethings there". Prefers tight label-value rows: a fixed/min-width label column with values sitting right next to the label at a consistent small gap, rather than stretched to opposite edges. Confidence: 0.7
- On mobile, modal cards/content must cover the full screen width — a panel that only spans part of the viewport with a big empty gap on one side is reported as broken ("this part isnt covering the whole screen horizontally"). Treats partial-width letterboxing as a layout bug, not acceptable whitespace. Confidence: 0.7
- Wants redundant/self-evident status indicators removed entirely, not just conditionally hidden — the "Nivel" pill under every measurement section (which was already hidden when level) was called out as noise on "every one of the sections" with "remove it," meaning delete the element everywhere (all sections, all code paths), not leave it for non-level states. Confidence: 0.6
- Expects placed annotations (text boxes/labels in the photo editor) to be movable after placement — asked "How can I move a textbox after placing it?" and was met with the fact that annotations are baked into `customStrokes` with no select/drag; the expectation is a select-and-drag-to-move interaction, not undo-and-replace. Confidence: 0.6
- On mobile, when content (e.g., a tall photo) would overflow vertically, the primary action/navigation buttons must stay reachable — the bottom button menu should be pinned sticky to the bottom of the scroll panel (always horizontal, z-index above content) rather than scrolling out of view behind the tall content. Confidence: 0.7
- Tall photos/images in mobile layouts should be height-capped relative to the viewport (e.g., `max-height: 60vh` with aspect preserved) so they never balloon the panel and push controls off-screen. Confidence: 0.6
- On mobile, bottom panels/containers must be unscrollable — prefers the panel to size exactly to its content (removing arbitrary vh `max-height` caps and `overflow-y: auto`) with the flexible canvas/upper area absorbing the shrink, so there is never an internal scrollbar, even when content is slightly taller than the capped height ("make that unscrollable"). Confidence: 0.7
- Prefers content-driven responsive layouts over fixed-width breakpoints: elements should stay side-by-side whenever they fit and only stack vertically when the normal arrangement would actually overflow — natural flex-basis wrapping (`flex: 1 1 <min-useful-width>` + `flex-wrap: wrap`), not a blanket `@media (max-width: Npx) { flex: 1 1 100% }` that stacks even when there's room ("it should only apply if the normal arrangement of items overflows"). Confidence: 0.8
- Expects responsive behavior (e.g., vertical stacking of input rows) to apply consistently across all steps/sections of a multi-step form — flagged "the verticalness is only working on step 2???" when other steps behaved differently on the same screen. Confidence: 0.5
- When a modal is open, the page behind it must not scroll — opening a modal should lock body scroll (released on close) so sticky headers/backdrops stay put and the modal scrolls internally; a modal that lets the background page scroll was reported as a bug ("dashboard scrolls the top bar instead of the modal for the job when focused on one?"). Confidence: 0.6
- Key graph annotations (e.g., desnivel offset arrows + labels) must stay visible inside the focused viewport when the user zooms in — positioning them at edge corners that land off-screen at the zoom level was reported as a bug ("the limits for not showing the offsets on the main graph are too close on zoom-in"); they should be drawn at the visible midpoint of the edge (center of the focus region), not near the clipped extremes. Confidence: 0.5
- Wants repeated components across a multi-step wizard/form to share the same design language and structure — when one step's button row renders differently from its siblings (e.g., the Next button stretched by odd flex nesting → "EXTREMELY padded to the right"), it's reported as a bug and expected to match the other steps exactly ("make it use the same design language as the other steps"). Pushed back again after the fix ("ok ykw can we put the step 2 layout back to how steps 1, 3, 5, 6 and 7 have it"), naming the reference steps explicitly — the dominant pattern across the majority of steps is the source of truth and the deviating step must be conformed to it. Confidence: 0.9
